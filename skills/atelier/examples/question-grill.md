## 結論 {span=2}
```callout info この回で決める点は 3 つ
見積もりの書き出しで、出力の形・保存の場所・失敗したときの扱いの 3 つを決めます。3 つとも推す答えのとおりなら、書き出しは 1 つのボタンから PDF になり、失敗しても画面の入力は消えません。
```

## 今の流れ
```flow
(見積もりを作る) -> 画面で見る
画面で見る -> 画面を印刷する
画面を印刷する -> 余白や改ページが手作業になる
```

## 答えたあとの流れ
```flow
(見積もりを作る) -> 画面で見る
- 画面で見る -> 画面を印刷する
- 画面を印刷する -> 余白や改ページが手作業になる
+ 画面で見る -> 書き出しのボタンを押す
+ 書き出しのボタンを押す -> PDF が端末のダウンロードに入る
+ 書き出しのボタンを押す -> 失敗の表示を出して、入力はそのまま残す: 失敗したとき
```

## 決めること {span=2}
```ask
Q1 書き出しの形を PDF にしますか
* はい (PDF) | そのまま共有や印刷ができる。レイアウトは固定になる
- いいえ、画像 (PNG) にする | 作りは簡単だが、文字の選択ができない
```

```ask
Q2 書き出したファイルは端末のダウンロードに入れますか
* はい (端末のダウンロード) | サーバーには何も残らない。持ち主が自分で管理する
- いいえ、サーバーに保存して一覧に出す | あとから見返せる。保存の置き場と消す決まりが要る
```

```ask
Q3 書き出しに失敗したときは、失敗の表示を出して入力を残しますか
* はい (入力を残す) | やり直しがすぐできる。表示の文言を 1 つ足す
- いいえ、画面を最初の状態に戻す | 実装は単純だが、入力が消える
```

## 判断の材料 {span=2}
| 点 | 推す答えを選ぶ理由 |
|---|---|
| Q1 | 見積もりは取引先に渡す紙として使われる。文字を選べる形のほうが扱いやすい |
| Q2 | 今のシミュレーターはサーバーに利用者のデータを置かない。この方針を変えない |
| Q3 | 入力に時間がかかる。消えると利用者の負担が大きい |
