# Atelier v8 の作り直し: 決まったこと（grill、2026-11-16）

前提: 調べる（OMM の差分キャッシュ・安いモデル）→ 決める（強いモデル、事実の束だけで、決まった場所で 1 回ずつ）→ 確かめる（スクリプト）。
残す: 進行役が出番を 1 つずつ渡す形、最後の見直し 1 回 + 修正の段、モデルなしの E2E スクリプト、承認ページ。

- Q1 reeschan/atelier に v8 として新しく作る。v7.15 は参考。v7 の run は引き継がない
- Q2 進行役スクリプトは残す。持つのは次の作業の選択・回数の上限・予算・関門・トークンの記録だけ。workflows には乗せない
- Q3 PBI ごとの LLM の見直しはやめる。wave ごとは機械の検査だけ。LLM の見直しは最後の 1 回
- Q4 機械の検査で落ちたら、失敗の出力と差分だけを渡して同じ実装役に 1 回だけ自動で直させる。まだ落ちたらユーザーに聞く
- Q5→Q15 で再検討中（段の作り）。承認ページに当たった規則と入力の値を出すことは決まり
- Q6 役ごとのモデルは設定 1 か所だけ。文書にモデル名を書かない。run の始めに役とモデルを承認ページに出す
- Q7 起動ごとに役・モデル・トークン・費用を記録。報告に PBI・役・モデル別の合計。取れないものは「不明」
- Q8 承認後の取り決めの変更は追記。古さの検査は依存する PBI だけ
- Q9 v8 の核は 調べる→設計→承認→wave の実装と機械の検査→最後の見直し→修正→E2E→報告 と複数の実行先。Jev・lint・見た目づくり・marketing・security・優先テンプレート・交互グループ・Kiln・Studio/desk・headless 設計役・inline は後で個別に
- Q11・Q12 取り下げ
- Q13 sensitive は決める役が候補と理由を出すだけ。ユーザーが承認ページで決める。sensitive は run から外し、引き継ぎメモを書いて別セッション/設計を提案。依存 PBI は保留（ユーザーが前提なしで進めてよいと言ったものだけ進める）。テンプレートに sensitive の規則は持たない
- Q14 テンプレートを 1 種類に（実装の規則・役・上限・部品のオン/オフ）。優先テンプレートは期限つきの切り替え。agents.json は実行先の登録だけ
- Q15 保留: 段を Claude のモデル名にしない。何段にするかは外部事例の調査待ち
- Q16 経路の最後を Claude にする決まりはやめる。全部使えなければ聞く。既定のテンプレートは最後を Claude に
- Q17 注意書きは持たずに始め、棚卸しからユーザーが選ぶ。残すものもできるだけ機械の検査に
- Q18 注意書きは A の 4 系統だけ残す。B・C は捨てる。CLI の癖はスクリプトとテストへ
- Q19 A を 14 の規則（G1〜G14）に抽象化。止め方は ①起動前 ②進行役が拒否 ③事後の検査 ④指示文。指示文に残るのは G12 の判断と G13 だけ。①〜③を先に作る
- Q15a 段は L1〜L5（モデル名なし）。テンプレートに「段→経路（実行先・モデル・effort）」の表。隣の段が同じモデルで effort 違いも可
- Q15b 段の定義（熟練者の所要時間の見当＋設計判断の要否、例つき）は v8 に同梱。テンプレートは表だけ変えられる
- Q15c 段は決める役が理由つきで付け、承認ページに段・理由・規則・モデルを出す。ユーザーが変えられる。リスクの軸は核に持たない
- Q15d 自動の 1 回でも落ちたら、選択肢に「1 段上の経路で作り直す」。段×モデルの初回合格率を報告に出す。表はユーザーが直す
- （追加の要望 2026-11-16）規則ごとに、直した回数・どれだけ気にしたかを metrics に。読み込みの文脈に対して、規則が成果物の質にどれだけ効くかを見たい → Q20〜
- Q20 規則に ID。起動ごと（読ませた規則とトークン）・検査ごと（発火、段・モデル・L 段）・直しごと（自動か聞いたか）を記録。報告に規則ごとの合計
- Q21 指示文の全節と事実の束にも ID を付け、起動ごとの読み物の内訳（節ごとのトークン）を記録
- Q22 テンプレートで④の規則と節を「読ませる/読ませない」に切り替え可（既定は読ませる）。違反率・初回合格率・指摘数を並べるが「効いた」とは書かない
- Q23 「気にした度合い」は「読ませたのに違反した回数」で見る。自己申告は取らない
- Q24 層は 2 つ。LLM の役はすべて呼び出し側が進行役の指示で深さ 1 で起動。外部 CLI は進行役のスクリプトが起動
- Q25 最後の見直しは指摘に重さと確かさ。進行役が確かさ 80 未満と軽い書き方を捨てる。残りを決める役が 1 回仕分け（直す/見送る/聞く）。直す一覧はユーザーの承認後に修正の段へ
- Q26 修正の差分は機械の検査と E2E だけ。E2E 失敗で修正に戻すのは上限まで（既定 2）、超えたら聞く
- Q27 テンプレートの上限に run 全体のトークン/費用の上限を書ける。超えそうなら起動前に聞く。既定は上限なし
- Q28 light の道は持たない。小さければ Atelier を使わないと言って終える
- Q29 事実の束は 1 つの JSON。モジュール・層・触りそうなファイル・既存のテスト・規約、項目ごとに出典。安いモデル＋OMM の差分キャッシュで作る。共有メモリは決める役が ID 指定で読むだけ
- Q30 hill-climb の実験の仕組み（events・task_profile・splits・failures・changes・ingest・export_cases・leakcheck）は核に入れない。記録を 1 起動 1 行の JSON にして後でつなげるようにする
- Q31（撤回）→ Q31' 入口に「詰める」段（grill→仕様）を置く。仕様の有無は機械が見て、飛ばすかはユーザーが 1 問で決める
- Q32 承認ページ: 役とモデル・テンプレート / PBI 表（L 段・理由・規則・経路）/ sensitive の候補 / 外部へ送る PBI / 上限と見積もり / 決めること
- Q33 決める役を呼ぶのは 詰める段のあと PBI を書く・承認で直す・最後の見直しの仕分け の 3 回だけ。途中で計画が崩れたらユーザーに聞く
- Q34 詰める役は決める役と別の役（テンプレートの役）。決める役には仕様と事実の束だけ渡す
- Q35' 設計の木のファイルは決まったこと 1 行ずつ＋未決の問いの一覧だけ。巡ごとに新しく起動し、手順・事実の束・このファイルだけを同じ順で読ませる（キャッシュが効くように）
- Q36 仕様は design-flow と同じ to-spec の章立て。仕様の合意も PBI の承認も今と同じ answer-me-with-html の HTML ページ
- Q37 修正役は置かない。実装役が直しの一覧のまとまりを受け取って作る。修正のモデルはテンプレートの役で別に決められる
- Q38 用語は v8-GLOSSARY.draft.md のとおり。難度（L1〜L5）・工程・「段」は使わない。設計役・出番の語はなくす
