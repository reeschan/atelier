# 仕様: pbi-orchestration-jev の汎用化と整理

- 状態: 合意済み (2026-10-21、design-flow v1 / grilling 3 回)
- 対象: このリポジトリのスキル pbi-orchestration-jev 全体 (指示文・スクリプト・編集画面・README)
- 実装: 3 つの段に分け、各段を 1 つの PR にする。実装は pbi-orchestration-jev v20 で PBI に分けて進める

## Problem Statement

pbi-orchestration-jev は v1 から v20 まで機能を足し続けた結果、作者 1 人の環境と運用に寄った形になっている。

- 誰かがリポジトリから入れても、そのままでは動きにくい。既定の振り分け表は作者の契約 (OpenCode Go の DeepSeek、Codex の特定モデル、Antigravity の特定モデル) を前提にしており、期限の日付がコードに直書きされている。CLI を持たない利用者は、PBI ごとに「使えない → 再実行 → 次へ」を何段も踏む。
- 作者が期限付きで使っている優先テンプレートが、製品の一部のように見える。優先テンプレートは本来、利用者が自分で作るものである。
- 個人の設定 (振り分け・優先テンプレート・適用・Web ページの URL) はスキルのディレクトリの中に置かれる。更新でディレクトリを置き換えると消える。手元の版管理の配置だけを特別扱いするコードもある。
- Jev や Web ページ (claude.ai の Artifact) が無い環境では、振り分けがほぼ 1 つの段に固定され、優先テンプレートの正本 (Web の DB) にも届かない。
- 使える実行先とモデルを、利用者が把握して選ぶ手段が無い。モデル名は手で書くしかない。
- 指示文は散漫になっている。同じ規則の重複が 17 組あり、章番号が欠けていて (4・6.2)、20 か所以上が番号で逆参照している。用語は揺れており (設計者 / オーケストレーター、「昇格」の 2 つの意味)、出どころの書かれていない数値もある。毎ターン読まれる本文の 3〜4 割は、毎回読む必要が無い。
- Jev のゲートは、1 だけがスクリプトで、2・3 は手作業になっている。jev-log は誰にも読まれないまま増え続けている (1 リポジトリで 2,319 行)。sensitive な PBI の本文も Jev に送っており、外部に出す範囲が実行先の基準と食い違っている。

## Solution

リポジトリを製品の唯一の正本にし、誰がインストールしても使える汎用のスキルに作り替える。作者の手元も「公開版 + 個人の設定」という、ほかの利用者と同じ形にそろえる。

- 必須は Claude Code だけにする。Jev・shared-memory・外部の CLI (opencode / Codex / Antigravity / DeepSeek Harness)・Web ページ・rtk は、どれもあれば使う任意の部品にする。どれが欠けても止まらず、品質も大きくは落ちない。
- 入れた直後は、全段を Claude Code のサブエージェント (agent) で動かす。外部の実行先は、利用者が自分の振り分けテンプレートに書いたときだけ使う。5 つの実行先はすべて残し、プロバイダーを選べる価値を保つ。
- 初回の起動とセットアップで、使えるエージェントを検出して確認する。実行先ごとに使えるモデルを CLI から取得してローカルに控え、1 つの編集画面で「エージェントとモデル」「振り分けテンプレート」「優先テンプレートと適用」を組めるようにする。shared-memory・Jev・rtk は、任意の連携として案内する。
- 個人の設定はすべて、スキルの外の home に置く。スキルのディレクトリは丸ごと置き換えて更新できるようにする。
- 指示文は英語で書き直し、本文 / appendix / prompts の 3 種類に組み替える。規約は「正本は 1 か所」「数値に理由」「目指す形で書く」。

## User Stories

## Implementation Decisions

### 段 1: 汎用化の土台

- **原則**: 必須は Claude Code だけ。任意の部品が欠けたときのふるまいを、部品ごとに 1 つ決める (下の各項)。
- **home**: 個人の設定はすべて home に置く。中身は、振り分けテンプレート・優先テンプレート・適用・Web ページの URL・エージェントとモデルの選択・取得したモデル一覧・単価の上書き。
  - 既定の場所はスキルの外のユーザー設定ディレクトリ。環境変数 `PBI_HOME` で変えられる。コマンドの `--home` が最優先。
  - 版管理の配置を見分ける特別扱い (親のディレクトリ名が `versions` か) は消す。
- **既定の振り分け**:
  - 同梱の既定の振り分けテンプレートは、全段 agent だけにする (haiku・sonnet・opus のサブエージェント)。
  - コード内の振り分け表・期限の定数・特定のモデル名は消す。既定値の正本は同梱の既定の振り分けファイル 1 つにする。
  - 作者の並びは、見本の振り分けテンプレートとして examples に置く。
- **振り分けの解決順**: 作業リポジトリの振り分けテンプレート → home の振り分けテンプレート → 同梱の既定。優先テンプレートは、決定表のあと、振り分けテンプレートより先に当たる (今と同じ)。sensitive な PBI には当たらない。最後の手順は、振り分けテンプレートのその段の agent。
- **実行先とモデルの照合 (prepare.py)**: 開始時に、各手順を次の 3 点で照合する。合わない手順は外し、承認一覧の先頭と理由の列に出す。作業は止めない。
  1. 実行先が「使う」になっているか (agents.json)
  2. その CLI が見つかるか
  3. そのモデルにチェックが付いているか
  - agents.json が無いときは、照合を「CLI が見つかるか」だけにする。
- **承認一覧の表**: prepare.py は select_model の判定をそのまま出す。列は「段・route の先頭・review・補正後の値・理由・優先テンプレート・外した手順」。生の Jev の値だけを出して段と食い違って見える、という状態をなくす。
- **Jev が無いとき**: facts (変更ファイル数・モジュール数・sensitive) だけで段を決める、決定論的な規則にする。「Jev の値が無ければ 1」で sonnet に寄る今の動きはやめる。規則の中身は実装で決め、理由を添えてコードの 1 か所に置く。
- **Jev の役割**:
  - ゲート 1 (brief と PBI の品質による段の判定) とゲート 3b (差し戻し文の点検) に使う。
  - ゲート 2 (報告の仕分け) は、実装担当の状態の 1 行 (DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED) と検証コマンドの終了コードで機械的に行い、2 つが食い違うときだけ Jev に聞く。
  - ゲート 3a (修正の規模の判定) は廃止する。
  - sensitive な PBI は品質のチェックを飛ばし、brief だけを送る。
  - 読まれていない設定のしきい値は、どちらか 1 か所 (コードが読む設定) にそろえる。
- **jev-log**: 答えが前回と変わったとき・引き継ぎ・設計者が決定表を上書きしたときだけ書く。
- **tier up**:
  - 実行先ごとに決め打ちしたモデルの格上げ (ハードコードされたモデル名) は廃止する。
  - 止まったときの選択肢「段を上げて再実行」は残す。上げた先の route は、その時点の振り分けから引く。
  - 入口は prepare.py の `--only` と段の指定の 1 つにまとめ、route.json を書き直す (record_run が正しい実行先を読めるように)。
- **費用**:
  - 同梱の単価表は見本 (確認日つき) で、home の単価表で上書きできる。
  - 単価の分からないモデルは「不明」と件数で出す。
  - 設計者の費用は、agent_stats に API 換算で金額を出す機能を足す。
- **共通の関数**: 長いパス・JSON の読み込み・時刻・報告名の解析・ラベルなど、複数のスクリプトに重複している小さな関数を、共通のモジュール 1 本に寄せる。スクリプトはルートに平置きのまま (lib/ への移動はしない。home の解決を壊すため)。
- **見本と経緯の整理**:
  - 同梱の優先テンプレートは、中立な名前の見本だけを examples に置く。
  - 作者の運用の経緯 (移行手順・日付・作者の実測) は公開の docs から消し、残す価値のある判断だけ ADR にする。
  - テストの中の個人的な名前は、中立な名前に替える。
  - 品質・価格のカタログから、直書きの見本モデルと期限を消す。
- **スキルの版の記録**: STATUS.md の先頭にスキルの版を書く。
- **作者の設定の移行** (リポジトリの外の作業。段 1 の PR と同時に行う):
  - home に次を置く: agents.json (5 つの実行先すべて「使う」、今のモデルにチェック)、振り分けテンプレート (今の既定の並び、Codex の期限 2026-10-23 を手順の until に)、3 つの優先テンプレート、適用、Web ページの URL、dsh の単価
  - 環境変数で受ける: home・dsh の場所・共有の Jev クライアント
  - 移したあと、新しい版で prepare.py を空打ちし、今と同じ route が出ることを確かめる

### 段 2: セットアップと編集画面

- **入口 (スキルの引数)**:

  | 引数 | ふるまい |
  |---|---|
  | なし | 通常の実行。agents.json が無ければ、最初に「今セットアップ / agent だけで始める」を 1 問だけ聞く |
  | `setup` | ヒアリング → モデルの取得 → 編集画面の起動 → 任意の連携の案内。いつでも再実行できる |
  | `models` | モデルの一覧だけを取り直す |
  | `templates` | 編集画面を起動する |
  | `resume` | 今と同じ |

- **セットアップ用のスクリプト** (新設。検出とモデルの取得を受け持つ):
  - **検出**: opencode・codex・agy・dsh の CLI を探す。PATH に加えて fnm・nvm のグローバルも探し、dsh は専用の環境変数も見る。agent は常にある。結果 (場所・版) を返す。
  - **ヒアリングの記録**: 設計者が AskUserQuestion の複数選択 1 問で確かめた結果を agents.json に書く。
  - **モデルの取得**: 実行先ごとの取り方は次の表のとおり (2026-10 に実機で確認)。実行先ごとの取得は失敗しても他に波及させず、取れなかった実行先は「手入力で足せる」状態にする。

  | 実行先 | 取り方 | effort の取り方 |
  |---|---|---|
  | opencode | `opencode models --standalone` (1 行に 1 つ) | opencode のキャッシュにあるモデル情報 |
  | codex | `codex debug models` (JSON) | 同じ JSON の reasoning levels |
  | agy | `agy models` (タブ区切り) | ID の末尾 |
  | dsh | 一覧のコマンドは無い。同梱のカタログ JSON と `--dump-config` | カタログの thinking level |
  | agent | Agent ツールの定義 (haiku・sonnet・opus・fable) | low〜max |

  - 取り方の細部は、実行先の版で変わりうる。「既知の問題」として版と確認日を添えて書く。
- **ローカルの形**:

  | ファイル | 中身 | 性質 |
  |---|---|---|
  | agents.json | 実行先ごとの「使うか・CLI の場所・版・確認日時・選んだモデル (と任意の課金の種類)」 | 利用者が決めたこと |
  | models/<実行先>.json | 「取得日時・取得方法 (CLI / 手入力)・モデルごとの ID と effort」 | 取得した一覧の控え |

  - 取り直すと models だけが更新され、選んだモデルは残る。一覧から消えたモデルが選ばれていれば警告する。
- **編集画面**: 今の Template Studio (ローカルのサーバーとページ) を 1 つに統合する。保存先はすべて home。タブは次の 3 つ。
  1. **エージェントとモデル**: 実行先ごとに、検索とチェックボックスで選ぶ。取得日時を出す。手入力で足せる。品質・価格は参考情報として横に添える。
  2. **振り分けテンプレート**: 段ごとに手順を組む。モデルの選択肢は 1 で選んだものだけ。
  3. **優先テンプレートと適用**: 作成・編集 (交互グループを含む)、期限と期限切れの扱いを付けた適用。opus の段を上書きしていれば注意を出す。
- **優先テンプレートの正本**: ローカルのファイル。claude.ai の Artifact のページは任意の同期先で、あれば開始時に同期する。無ければ何もしない。チャットでの適用と期限切れの確認は、ローカルだけで完結する。
- **任意の連携の案内** (setup の最後):
  - **shared-memory**: メモリの MCP (search / get / write) がつながっているかを確かめる。無ければ https://github.com/reeschan/shared-memory を示し、その README のセットアップを読みながら一緒に進め、登録は mcp-setup に渡す。手順はこのスキルに書き写さない。OS についての注記も書かない。
  - **Jev**: API キーは環境変数で受け、設定ファイルの作り方を案内する。
  - **rtk**: フックの登録内容を見せ、承認を得てから行う。
- 段 2 で新しく書く appendix は、最初から英語・新しい規約で書く。

### 段 3: 指示文の書き直し

- 状態: Atelier の PR 2 で行った (docs/specs/atelier-workflow.md の「エンジン化と指示文 (PR 2)」)。

- **言語**: エージェントが読む指示文 (本文・appendix・実行先の手引き・実装担当の手引き・prompts) を英語にする。応答は利用者の言語。README は英語と日本語。用語集 (CONTEXT.md) はスキルのディレクトリの中に移し、英語と日本語の対訳にする。
- **呼び名**:

  | 英語 | 日本語の対訳 |
  |---|---|
  | orchestrator | 設計者 |
  | worker | 実装担当 |
  | runner | 実行先 |
  | tier / tier up | 段 / 段上げ |
  | promotion (メモリ側だけ) | 昇格 |

  - ほかに、wave・report name・gate・work root・ref を定義する。
- **構成**:

  | 種類 | 読み方 | 中身 |
  |---|---|---|
  | 本文 | 毎ターン読む。約 110 行・5,000 トークン未満が上限 | 止まる場面・不変条件・「事象 → 読む 1 本」の表・開始・起票と担当決めと承認・1 PBI のチェックリスト・文脈を細く保つ規則・作業メモリの要点 |
  | appendix | 事象が起きたら 1 本だけ読む。ディレクトリ名は今のまま | 起票の雛形と検証コマンドの書き方・実行先・差し戻しと止まる・引き継ぎと resume・完了・作業メモリ・優先テンプレート・セットアップと編集画面 |
  | prompts | サブエージェントにパスで渡すだけ。設計者は読まない | 依頼文の雛形・レビューの依頼・設計見直しの依頼・実装担当の手引き |

- **書きぶりの規約**:
  - 章番号を使わず、見出し名で参照する
  - 同じ規則は 1 か所だけに書く
  - スクリプトの中身 (決定表など) を書き写さない
  - 数値には理由を 1 句添える
  - 禁止形は、目指す形に書き換える
  - 長い 1 文を、条件ごとに分ける
  - 日付つきの状況や作者の実測値は、本文に置かない
  - description は「いつ使うか」だけにする
  - 規約は shared-memory に review-guideline として残す
- **実行先の手引き**: 共通の決まり (使えないときの扱い・CLAUDE.md を読まないこと・依頼文の置き場) を 1 節にまとめる。各実行先は「前提 / 起動 / 使えない印の表 / 既知の問題 (確認日・版つき、OS の事情を含む)」の同じ型で書く。モデル名は書かない。
- **インストールと更新**:
  - 入れ方: clone したリポジトリのスキルのディレクトリを、ユーザーのスキルの置き場にコピーする (リンクも可)
  - 更新: 丸ごと置き換える
  - 初回の起動で setup に誘導する
  - リリースにタグを付け、README に Upgrading 節を置く

## Testing Decisions

- **良いテストの基準**: スクリプトを CLI として、一時のディレクトリ (作業リポジトリの docs/pbi と home) で動かし、出力 (表・JSON ファイル) だけを見る。内部の関数の形には依存しない。外部の CLI は、PATH の先頭に置いた小さな偽の実行ファイルで置き換える。ネットワークにも本物の CLI にも触れない。
- **合意済みの seam** (2026-10-21 にユーザーと合意):
  1. **S1 prepare.py の CLI**: 一時の docs/pbi・一時の home・偽の CLI を置いた PATH で実行し、表と route.json を見る。次をここで確かめる。
     - 既定の振り分け (全段 agent)
     - 実行先の検出と照合による手順の外しと警告
     - Jev が無いときの段の規則
     - 優先テンプレートの当て方 (opus の段の注意を含む)
     - sensitive の扱い
     - tier up
     - jev-log が変化のときだけ書かれること
  2. **S2 セットアップ用スクリプトの CLI**: 偽の opencode / codex / agy / dsh (それぞれ実機と同じ形式の出力を返す) を置いて検出とモデルの取得を実行し、agents.json と models/*.json を見る。次をここで確かめる。
     - 取り直しで選択が残ること
     - 消えたモデルの警告
     - 取れなかった実行先の扱い
  3. **S3 編集画面のサーバーの HTTP API**: 一時の home への読み書きを確かめる。対象は、エージェントとモデル・振り分けテンプレート・優先テンプレートと適用。画面の見た目は自動テストしない。
  4. **S4 指示文の参照の実在**: 本文と appendix が指すパスと見出しが存在すること、本文の行数とトークンの上限を確かめる。
- **既存のテストの扱い**: 今の unittest (root 189 件・jev 14 件・studio 10 件) は通す。studio のテストは、今は起動の仕方の不備で走っていないので、走るように直す。個人的な名前は中立な名前に替える。
- **先行例**: prepare.py の CLI テスト、select_model の決定表のテスト、templates.py の検証のテスト、編集画面のサーバーのテスト、record_run の生ログからの読み取りのテスト。
- **自動テストでない確認**:
  - 作者の設定を移したあとの prepare.py の空打ち (今と同じ route が出ること)
  - 固定の小さな作業 (3 PBI・2 波・差し戻し 1 回・外部の実行先 1 回) を v20 と新しい版で 1 回ずつ流し、設計者のキャッシュの読み込み・ターン数・止まった場面・実行の記録を比べる。v20 の基準値は、書き直しの前に取っておく。
