# 仕様: フェーズ・アダプター (任意で入っている設計・レビューのスキルを、決まったフェーズで使う)

- 状態: 合意済み (2026-10-21、design-flow v1 / Ultracode、grilling 6 回・21 問)
- 前提: 段 2 (セットアップと編集画面、PR #14) はマージ済み。段 3 (指示文の英語化と約 110 行への削減) より前に入れ、段 3 はこの仕様の行も含めて書き直す。
- 調査の出典: 実行中のフェーズの地図、Claude Code のスキルの仕組み (公式ドキュメント)、呼び出し先の候補の性質、3 案の比較 (2026-10-21 の Workflow)。

## Problem Statement

このスキルは、複数ファイルにまたがる実装を PBI に分けて進める。ただ、設計と全体のレビューは、スキルの中では薄い。設計は「既存コードを調べて設計を決める」の 1 文だけで、決めたことも残らない。最終の確認も、設計者が全体の diff を読み直すだけである。

作者は、設計を design-flow、レビューを review-flow という自分の個人スキルで補い、グローバルの CLAUDE.md でそちらへ振り分けている。一般の利用者にはその仕組みが無い。一方で、mattpocock-skills (MIT、公式マーケットプレイス) のように、設計の詰め (grilling) や 2 軸のコードレビューを持つ公開スキルを入れている人は多い。Claude Code にも、built-in の `/code-review` と `/security-review` がある。

利用者から見た問題は 3 つある。

- 良い設計・レビューのスキルが入っていても、このスキルはそれを使わない。
- 使わせようとして自分で指示を足すと、呼び合い (design-flow → このスキル → design-flow) や、勝手な副作用 (PR へのコメント投稿、実装の開始) が起きうる。
- 何も入れていない人は、設計の前提がどこにも残らない。

## Solution

**アダプター**を足す。アダプターは、決まった**フェーズ**で、利用者の環境に任意で入っている別のスキル (**呼び出し先**) を呼ぶための取り決めである。いつ呼ぶか、何を渡し何を受け取るか、何を禁じるかを決める。

- **フェーズは 3 つ**: 設計 (分解の前)、最終レビュー (全 PBI のあと)、セキュリティレビュー (最終レビューと同じ時点で、sensitive か deep な作業があるとき)。
- **呼び出し先**は、スキルに同梱する「既知の名前の表」にあるものだけを自動で使う。v1 の表は、mattpocock-skills の grilling・domain-modeling・code-review と、built-in の `/code-review`・`/security-review`。作者の design-flow・review-flow は呼ばない (作者の個人スキルとしてそのまま残す)。
- **入っていなければ**、そのフェーズは組み込みの手順で進む。何も入れていない人でも、built-in のレビュー 2 つは Claude Code に最初から入っているので動く。何も無くなるのは設計だけで、そこには短い組み込みの手順を足す。
- **使うかの決め方**: 明らかに複雑なら聞かずに使う。明らかに単純なら黙って飛ばす。どちらとも言えないときだけ、分解の前に 1 回聞く。止まる場面は増やさない。
- **設定**: 設定なしで動く。home の `agents.json` の `adapters` で、フェーズごとに `auto` / `off` / スキル名に上書きできる。
- **おすすめのセット**: `setup --recommended` で mattpocock-skills を紹介する。ユーザーが 1 回承認したら、公式マーケットプレイスから入れる。同梱はしない。

## User Stories

### 何も入れていない利用者

1. As a 何も入れていない利用者, I want アダプターが無くても今までどおり最後まで動くこと, so that 入れた直後から使える
2. As a 何も入れていない利用者, I want 最終レビューに built-in の `/code-review` が自動で使われること, so that 追加のインストールなしで、独立した目のレビューが得られる
3. As a 何も入れていない利用者, I want sensitive か deep な作業があるときに built-in の `/security-review` が使われること, so that 認証や権限の変更を見落としにくい
4. As a 何も入れていない利用者, I want 明らかに複雑な依頼で、設計者が決めたことと置いた前提が文書に残ること, so that あとで判断の理由を追える
5. As a 何も入れていない利用者, I want 置いた前提が承認の一覧に「未決の前提」として数行載ること, so that 承認のときに前提を直せる
6. As a 何も入れていない利用者, I want 設計を深めたいときに mattpocock-skills を入れられると、一度だけ知らされること, so that 毎回の案内に煩わされない

### おすすめのセットを入れる利用者

7. As a 利用者, I want `setup --recommended` で、推奨スキルの名前・使うフェーズ・リンク・ライセンス・入れるコマンドを見られること, so that 何が入るかを理解してから決められる
8. As a 利用者, I want 1 回「はい」と答えるだけで、推奨スキルが公式マーケットプレイスから入ること, so that 手でコマンドを打たなくて済む
9. As a 利用者, I want 「いいえ」と答えたときや `claude` コマンドが無いときは、コマンドが表示されるだけになること, so that 自分の判断で入れられる
10. As a 利用者, I want 入れたあとに `/reload-plugins` か再起動が要ると案内されること, so that 入れたのに使われない理由で迷わない

### mattpocock-skills を入れている利用者

11. As a mattpocock-skills を入れている利用者, I want 明らかに複雑な依頼で、分解の前に grilling で設計を詰められること, so that 決めることの抜けが減る
12. As a 用語集を育てているリポジトリの利用者, I want 対象のリポジトリにもう GLOSSARY.md か CONTEXT.md があるときだけ、domain-modeling も使われること, so that 用語集の無いリポジトリに、PBI の外でファイルが増えない
13. As a 利用者, I want grilling のあとで、設計者が仕様を `docs/specs/` に書くこと, so that 最終レビューと resume がその仕様を使える
14. As a 利用者, I want 最終レビューに mattpocock-skills の code-review が、merge-base と仕様のパス付きで使われること, so that 規約と仕様の 2 軸で全体を見てもらえる
15. As a 利用者, I want 複数のレビューのスキルが入っているとき、決まった優先順で 1 つだけ使われること, so that 費用と結果が予測できる

### 決め方と止まり方

16. As a 利用者, I want 単純な依頼ではアダプターが黙って飛ばされること, so that 小さな作業が重くならない
17. As a 利用者, I want どちらとも言えない依頼では、分解の前に 1 回だけ聞かれること, so that PBI を作り直さずに済む

20. As a 利用者, I want 承認の一覧に、使う予定のアダプターが載ること, so that 承認の時点で何が動くかが分かる
21. As a 利用者, I want 全体の diff が小さく、PBI が少なく、deep も sensitive も無いときは最終レビューが飛ばされること, so that 小さな変更に余計な費用がかからない

### 設定

22. As a 利用者, I want `agents.json` の `adapters` で、フェーズごとにアダプターを止められること (`off`), so that 使いたくないフェーズを外せる
23. As a 利用者, I want `adapters` に既知の名前の表に無いスキル名を書けば、それを呼び出し先にできること, so that 自分のスキルや別の公開スキルを使える
24. As a 利用者, I want `adapters` に不正な値を書いたとき、その行が無視され、理由が表示されること, so that 設定の誤りで作業が止まらない
25. As a 利用者, I want 名前が似ているだけの未知のスキルが勝手に使われないこと, so that 実装を始めたり PR に投稿したりするスキルが紛れ込まない
26. As a 利用者, I want モデルから呼べないスキル (ユーザーが打つ前提のもの) が使われないこと, so that そのスキルの作者の意図が守られる

### 安全と記録

27. As a 利用者, I want レビューの呼び出し先が、コードを変えず、PR にも投稿しないこと, so that 合否と変更の主導権が設計者に残る
28. As a 利用者, I want 呼び出し先が何かを変えたら、その結果が捨てられて組み込みの手順に戻ること, so that 指示に従わない呼び出し先が作業を壊さない
29. As a 利用者, I want 呼び出し先が質問しようとしたら、組み込みの手順に戻ること, so that サブエージェントの中で答えの無い質問に詰まらない
30. As a 利用者, I want 最終レビューで本物と確かめられた指摘が、そのファイルを担当した PBI の差し戻しになること, so that 直す仕組みと回数の上限が今までと同じになる
31. As a 利用者, I want どの PBI も担当していないファイルへの指摘は、完了報告の「発見」に載ること, so that 新しい止まる場面が増えない
32. As a 利用者, I want 好みや書き方だけの指摘では差し戻されないこと, so that レビューのスキルの癖で作業が長引かない
33. As a 利用者, I want 各フェーズでアダプターを使ったか・飛ばしたか・戻したかと、その理由と指摘の件数が STATUS.md と HANDOFF.md に 1 行で残ること, so that 引き継ぎのあとも経緯が分かる
34. As a 利用者, I want sensitive な作業のセキュリティレビューが、外部のサービスを使わずに行われること, so that 機密の扱いが今までと変わらない

### 設計者と保守する人

35. As a 設計者, I want レビューの呼び出し先が包むサブエージェントの中で動き、件数と各 1 行だけが返ること, so that 設計者の文脈が細いまま保たれる
36. As a 設計者, I want 最終レビューを使うかの判定がスクリプトの表で返ること, so that 毎回同じ基準で決まる
37. As a 保守する人, I want アダプターの規則と既知の名前の表が 1 つの付録にまとまっていること, so that 呼び出し先を足すときに 1 か所だけ直せばよい
38. As a 保守する人, I want 表の各行に、渡すもの・受け取るもの・禁止する引数が書かれていること, so that 新しい呼び出し先の扱いを迷わない

## Implementation Decisions

### フェーズと呼び出し先

- **v1 のフェーズは 3 つ**: 設計・最終レビュー・セキュリティレビュー。PBI ごとのレビュー (8 章) と TDD は v1 に入れない。
  - PBI ごとのレビューを外す理由は 3 つ。PBI の数だけ費用が増える。レビュー役の `pbi-worker` に Skill ツールが無い (ツールの許可リストで外してあり、この禁止は残す)。`record_run.py` で実行とレビューを結び付けられなくなる。
  - TDD を外す理由は、外部の実行先が Claude のスキルを読めないため。
- **既知の名前の表**は付録に置き、行ごとに次を持つ。フェーズ、呼び出し名、優先順、渡すもの、受け取るもの、禁止する引数、リンク、ライセンス、対話の有無、呼び返すか。
- **v1 の表**:
  - 設計: `mattpocock-skills:grilling` (必須)、`mattpocock-skills:domain-modeling` (対象のリポジトリに GLOSSARY.md か CONTEXT.md があるときだけ)
  - 最終レビュー: 1. `mattpocock-skills:code-review` (merge-base と仕様のパスを渡す)、2. built-in の `/code-review` (レベルを `medium` に固定し、フラグは付けない)、3. どちらも無ければ組み込みの手順 (今の完了時の全体の確認)
  - セキュリティ: built-in の `/security-review` だけ
- **作者の design-flow と review-flow** は表に載せず、呼ばない。作者の個人スキルとして変えずに残す。呼ばないので呼び合いは起きず、委譲 (yield) の仕組みは v1 では作らない。
- **見つけ方**: Claude Code が文脈に載せるスキルの一覧の名前で見つける。スキル名は必ず載るが、説明文は予算を超えると落ちることがあるので、名前で照合する。ディスクの走査はしない (無効にしたプラグイン、権限の deny、再読み込み前の状態を再現できないため)。
- **自動で使うのは表にある名前だけ**。名前が似ているだけの未知のスキルは使わない。理由は、PR に投稿する、実装を始める、spec をコミットして別のスキルへ進む、といった呼び出し先があるため。
- **モデルから呼べないスキル** (`disable-model-invocation`) は使わない。to-spec もこれに当たるので、仕様は設計者自身が書く。

### 使うかの決め方

- **入口の規則**: 仕様のパスを渡されて起動したとき (または `docs/specs/*.md` を明示されたとき) は、設計は済んだものとして扱い、設計のアダプターを使わない。design-flow から入ったときもこの経路になる。
- **設計を使う基準** (分解の前なので、依頼文とリポジトリの下調べで決める):
  - **明らかに複雑 → 自動で使う**: 新しい概念・外部とのインターフェース・データモデルの変更のどれかがあり、かつ 2 つ以上のモジュールにまたがる見込み
  - **明らかに単純 → 飛ばす**: 方針が決まっている (仕様がある、前の作業の続き)、または 1 モジュールの中で PBI が 3 件以下の見込みで、新しい概念が無い
  - **それ以外 → 分解の前に AskUserQuestion で 1 回聞く**。答えは作業の state.json に残し、resume では聞き直さない。止まる場面は増やさない (承認・上限・破壊的な操作・引き継ぎの 4 つのまま)
- **最終レビューの基準**: 全体の diff が 300 行以下、PBI が 2 件以下、deep も sensitive も無い、のすべてを満たすときは飛ばす。それ以外は使う。300 行は、8 章で Opus にレビューを任せる境目と同じ。値はあとで runs.jsonl を見て調整する。
- **セキュリティレビューの基準**: sensitive か deep な PBI が 1 件でもあれば使う。
- **最終レビューの判定はスクリプトに任せる** (`adapter_gate`): 各 PBI の route.json と、全体の diff の numstat を入力に、フェーズごとに「使う / 飛ばす」と理由を表で返す。設計を使うかの判定は文章の規則のままにする。

### 呼び出し先の動かし方 (アダプターの契約)

- **設計**: メインのセッションで呼ぶ (ユーザーとの対話が要るため)。grilling のあと、設計者が仕様を `docs/specs/<slug>.md` に書く。既存の仕様の見出し (Problem Statement 〜 Further Notes) に合わせる。
- **レビュー系**: 包むサブエージェントの中で呼ぶ。description は `FINAL.review` / `FINAL.security`。
  - 結果は `docs/pbi/reviews/final.review.md` (セキュリティは `final.security.md`) に書かせる。1 行目は `findings: 重大,中,軽微`、続けて指摘を 1 件 1 行 (`- [重さ] file:line — なぜ — 再現`) で書く形にそろえる。
  - 設計者には、件数と各 1 行だけを返させる。
  - 契約はサブエージェントへの依頼文に書く。Skill の引数には書かない (外部のスキルは引数の旗を解釈しない。built-in の code-review は引数を対象とレベルとして読むため)。
- **渡すもの**: base (merge-base)、head、仕様のパス、「報告だけで、直さない・投稿しない」。最初から渡しておき、呼び出し先が聞く必要をなくす。
- **禁止する引数**: `--fix`・`--comment`・`ultra`・`--max-findings`。built-in の code-review の件数の上限は利用者の設定として残るので、アダプターからは変えない。
- **安全策**:
  - 呼ぶ前後で HEAD と `git status --porcelain` を比べる。何か変わっていたら、結果を捨てて組み込みの手順に戻し、理由を記録する。
  - 呼び出し先がユーザーに質問しようとしたら、包むサブエージェントは `BLOCKED` を返し、設計者は組み込みの手順に戻す。
- **指摘の扱い**: 指摘は鵜呑みにせず、設計者が確かめる。
  - 本物と認めた指摘は、そのファイルを担当した PBI の差し戻しにし、差し戻しの上限 2 回に数える。
  - どの PBI も担当していないファイルへの指摘は、完了報告の「発見」に書く。
  - 好みや書き方の指摘では差し戻さない。
  - record_run.py の入力は変えない。
- **記録**: STATUS.md と HANDOFF.md に、フェーズごとに `adapter <フェーズ>: <スキル> run|skip|fallback (<理由>) findings a,b,c` の 1 行を書く。承認の一覧にも、使う予定のアダプターを載せる。

### 呼び出し先が無いときの組み込みの設計

- 明らかに複雑で設計の呼び出し先が無いときは、設計者が、決めたことと置いた前提を `docs/specs/<slug>.md` に短く書く。承認の一覧に「未決の前提」として数行載せる。止まる場面は増やさず、承認のときに直せる。最終レビューの Spec 軸もこの文書を使う。
- 同じとき、承認の一覧に「設計を深めたいなら `setup --recommended` で mattpocock-skills を入れられます」と 1 行添える。一度出したら home に残し、以後は出さない。

### 設定

- home の `agents.json` に `adapters` を足す。キーは `design` / `review` / `security`、値は `auto` (既定) / `off` / スキル名。
  - スキル名は、表に無い呼び出し先を使う唯一の道である。
  - 不正な値 (未知のキー、文字列でない値) は、その行を無視し、理由を 1 行出す。
  - 既存のキー (runners など) は変えない。

### おすすめのセットとインストール

- `setup --recommended` を足す。推奨のセットは mattpocock-skills だけ (built-in のレビュー 2 つは入れなくても使える)。
- 流れ:
  1. 名前・使うフェーズ・リンク (github.com/mattpocock/skills)・ライセンス (MIT, Matt Pocock)・入れるコマンドを見せる。
  2. 1 回「はい」をもらえたら、設計者が `claude plugin install mattpocock-skills@claude-plugins-official --scope user` を実行する。
  3. 入れたあとは `/reload-plugins` か再起動を案内する。
  4. 「いいえ」のときや `claude` コマンドが無いときは、コマンドを表示するだけにする。
- **入れる処理は、同梱のスクリプトに書かない**。Agensi の自動スキャンは、パッケージのインストールを危険なコマンドとして検査するため。README の「Network access, files and permissions」の節にこの動きを書く。
- 推奨スキルは同梱しない。リンクと使い方だけを README と付録に載せる。

### 書く場所

- アダプターの規則と既知の名前の表は、新しい付録 (英語) に書く。
- SKILL.md には、フェーズごとに 1〜2 行の参照を足すだけにする (設計の前、承認、完了)。完了の付録には、最終レビューとセキュリティレビューの手順の参照を足す。setup の付録には `--recommended` を足す。
- README (英語・日本語) に、推奨スキル・アダプターの動き・止め方を書く。アーキテクチャ図は arch-diagram で描き直す。
- 用語「アダプター」「呼び出し先」「フェーズ」は CONTEXT.md に足した。

## Testing Decisions

- **良いテスト**: スクリプトの外から見える入出力 (CLI の引数・標準出力・終了コード、home のファイル) だけを確かめる。内部の関数の分け方には依存しない。既存のテストと同じく、一時ディレクトリの home と偽のリポジトリで動かす。
- **合意済みの seam**:
  1. **`adapter_gate` の CLI**: route.json と diff の numstat を入力に、「最終レビューを使う / 飛ばす」「セキュリティレビューを使う / 飛ばす」と理由を返す。境目 (299/300/301 行、PBI 2/3 件、deep・sensitive の有無、route.json が欠けた PBI) を表で並べたテストにする。前例は select_model.py と prepare.py の CLI のテスト。
  2. **`agents.json` の `adapters` の読み取り**: `auto` / `off` / スキル名の読み取り、既定値、不正な値の扱い (無視して理由を出す)、既存のキーを壊さないこと。前例は agents.py のテスト。
  3. **参照の実在**: 新しい付録と、表のファイル参照が実在すること。test_references.py の対象に入る。リンクの URL は形だけを確かめ、ネットワークには出ない。
- **テストしない部分**: Skill ツールで呼び出し先を実際に動かす部分は、自動テストを書けない。実装のあとに、mattpocock-skills を入れた環境と入れていない環境で一度ずつ通しで動かし、STATUS.md の adapter の行と、final.review.md の形を確かめる。
